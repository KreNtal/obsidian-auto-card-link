# Domain coverage

Working notes for which sites the fetcher handles, what has been checked, and what
is known to be impossible. Not user documentation — the README covers usage.

Legend: ✅ works · 🟡 works, caveats · ⏳ not yet checked · ❌ unreachable (don't retry)

## Dedicated fetchers

`docs/fetchers.md` indexes the same handlers, grouped by what the code actually does: **endpoint**
(answers from an API, oEmbed or JSON feed and never reads the page HTML), **page + endpoint** (reads
the page first, A3, and lets the endpoint add one field), **page** (our own request, with our own
headers and parsing) and **hook** (`fetchGeneric` plus an `isUnusable` or `goneCard` check, which
costs no extra request and has nothing to break). Each row carries the exact source, the requests
the happy path costs, whether it caches, what proves a dead link, and how fragile it is under A6.
Today: 22 endpoint, 13 page + endpoint, 11 page, 22 hook, with nine at `high` - Twitch, X, Printables,
LinkedIn, Notion, Etsy, Kick, and the page reads of TikTok profiles and AniList. That file is the index; the evidence and the reasoning stay here.

Sites with a handler in `link_metadata_fetcher.ts` (dispatched from `fetchForUrl`).
They answer from an API / oEmbed / JSON endpoint and never read the page HTML, so the
site name comes from `SITE_NAMES`, not `og:site_name`.

The `host` a card shows has a leading `www.` stripped in `fetch()`, once, for every path —
the generic one used to copy whatever the pasted URL happened to say, and the dedicated
fetchers were split roughly half and half between the two forms. Only the leading `www.`
goes: `open.spotify.com`, `en.wikipedia.org` and `clips.twitch.tv` keep their subdomain.
Nothing reads `host` for behaviour, so this is cosmetic; cards already in a vault keep the
form they were written with until refreshed.

`request()` passes `throw: false` to Obsidian's `requestUrl`. Without it requestUrl rejects on every non-2xx, the helper's catch swallows the response, and callers get `undefined` with no status - so until 2026-09-03 a 404 and a dead network were indistinguishable, every `res.status !== 200` test was really only testing `!res`, and the rule below could not fire. `fetchTitleOnly` now also refuses to read a 4xx/5xx page's own `<title>`: it names the error (“404 Not Found”, “Just a moment…”), not the link.

When a page is known not to be readable - a 404 or 410, an auth wall - the **title** comes from the URL (`buildUrlCard`, refined per site by `buildLinkedInFallback`, `buildXFallback`, `buildImdbFallback`), never from the error page, whose `<title>` names the error. Its `og:image` and `og:description` are kept, though: they are the site's own furniture, and Roberto's call (2026-09-03) is that a card carrying the site's graphic reads better than a bare one. Microlink is not asked at all. Once it has answered 429 once, the round trip is skipped for the rest of the session - the quota is daily and per IP, so every further call returns the same 429 - but the notice still fires. Roberto's call: knowing that a link is one the direct fetch cannot handle is worth a notice even on a day when nothing can be done about it, so the skip is about the wasted request, not about the signal. A card is still written either way: the reader gets the link they pasted, in the shape every other link has.

**Dead links follow field rules J1-J4 (2026-09-17).** A card for a link the site says is not there is built from the URL by one general builder and says so, the way the "Links that are not found" setting says: struck through by default, or a text of the user's own before it, or nothing. Since 2026-09-18 a card stores this as `status: not-found` in its block with the title left clean, and is marked when shown, so changing the setting changes every card; a markdown link is marked once when written (`~~…~~` natively struck, or the prefix). The first version, the day before, wrote the mark into every card's title. Rejected on the way, the same day: a " - not found" suffix (English in every vault, and cut off first by the card's two-line title clamp) and a 🚫 prefix. The builder was wrong in a way no site caused: it skipped an id at the end of the path and climbed to the route word before it, so a dead Codeberg issue, a GitHub pull request and a BBC story were titled "Issues", "Pull" and "Technology". Now a last segment with no letters gives the whole path verbatim (`forgejo/forgejo/issues/99999999`), a single token stays verbatim (`nonexistentorgxyz123`, no longer "Nonexistentorgxyz123"), and a slug of several words is still turned into prose. The marker is applied where the proof is established in the generic path - `errorPageCard` (401, 404, 410), `goneCard`, `emptyPage` - which covers every generic site and every hook; Google Maps, which used `goneCard` to retitle live places, now does it after `fetchGeneric` instead. **Dedicated fetchers were marked in one mechanical pass the same day**, on the branches this file already records as proof - no title changed, and no site was re-measured beyond confirming each proof still answers the same (2026-09-17): YouTube's 400/404, Vimeo's and Dailymotion's 404, Twitch's three shells and its stock "VOD - Twitch" page, Printables' `{"print":null}`, IMDb, GitHub's, GitLab's, Bitbucket's, npm's, crates.io's, Trello's and AniList's 404s, TikTok's 400, Steam's `success:false`, OpenStreetMap's 404/410, arXiv's empty feed, Stack Exchange's `items: []`, Hacker News' `null` and deleted items, Bluesky's 400 "not found", SoundCloud's homepage shell, Notion's 404 and dead-workspace shell, Discord's front page for an expired invite, a LinkedIn 404. Where a fetcher gave the same card to proof and to failure (Bitbucket, crates.io, AniList, Trello cards, YouTube), only the proof is marked and the failure keeps its unmarked card; Printables, Bluesky and Hacker News' helpers now return the proof distinctly instead of `undefined`. Not marked, on purpose: YouTube's 401 (possibly a live video with embedding off), LinkedIn's sign-in wall and X's syndication error page (both answer a live, protected or dead item alike - J1), Reddit (no proof branch at all). A dead arXiv id currently answers the API with **406**, so it reaches the `/abs/` page's own 404 and is marked there. Label helpers stay, under J3's clause on URL-shape labels. One bug surfaced: IMDb's suggestion endpoint is a search, and a dead id answered with look-alikes - `tt99999999` became "Space: 1999" - so only the entry carrying the id itself is taken now, and none is proof.

**Microlink's own error pages are refused too (2026-09-17).** `status: "success"` in its answer only means the API call worked; `statusCode` is what the page answered Microlink. On an eBay listing both came back as `"success"` and `403`, titled "Error Page | eBay" with the description "SORRY", and the plugin wrote that into the note. `fetchViaMicrolink` now rejects any `statusCode` of 400 or above - the line `fetchTitleOnly` already drew for its own read - and the link goes on to the card built from its URL.

**Hosts Microlink will not fetch are not sent twice (2026-09-17).** On the free tier Microlink refuses some domains outright with a 400 whose body carries `EPROXYNEEDED` - it wants its paid proxy. Measured on every Etsy route tried. Nothing about that changes within a session, so the host is remembered and later links on it skip Microlink - no "Fetching via external service" notice for a call that cannot succeed - and go straight to the card built from the URL. The first link on such a host still makes the call; the list lives in memory only.

Whatever the page did supply rides along with a URL-built card — description, image **and favicon**. The favicon was overlooked until 2026-09-07: `buildUrlCard` guesses `https://<host>/favicon.ico`, so a removed Medium article was handed that guess in place of the real `miro.medium.com` icon the page had just given us. `withPageFurniture` now carries all three, in `errorPageCard` and at both `goneCard` sites. Separately, a title is stripped of a separator left dangling at its end: a site that splits its own heading across `og:title` and `og:description` cuts at the punctuation and keeps it, so Medium publishes “Pandas v Psycopg:” and puts the rest in the description. No real title ends in `-`, `|`, `:`, `·`, `•`, `–` or `—`, so this runs for every site; a title that is nothing but punctuation is left alone rather than emptied.

**A page we refuse to believe still keeps its furniture.** Generalised on 2026-09-08, from Roberto's point that a `/channels/` Discord card had become two bare lines where the old generic read at least carried the site's blurb and artwork. What is wrong with a shell — Notion's, Discord's front page, LinkedIn's sign-in wall — is its **title**, which presents the site's own homepage as if it were the link. Its description and image are not wrong in that way: they are the site's furniture on a page we have established we cannot read, which is precisely the case `errorPageCard` has covered since 2026-09-03. So `withParsedFurniture` does for raw HTML what `withPageFurniture` does for an already-parsed card, and every fetcher holding a page it has decided not to trust now runs it through: Notion (the shell, and its error page), LinkedIn (the sign-in wall), Discord (both dead cases). Audited across the rest the same day, and it stops there for a reason: everywhere else the card is bare because the **page** is bare, not because anything was discarded. A dead Vimeo id answers 200 with no `<title>` and no og tags at all (7.5 KB of nothing, re-measured that day); YouTube, Dailymotion and Bluesky do the same for deleted content; Hacker News has never served an og tag; Stack Exchange and GitLab answer a 403 and a Cloudflare challenge. For those, adding furniture would mean spending an **extra** request to fetch a page already known to say nothing, which is the opposite of the rule two paragraphs down.

**When an endpoint proves a link is dead, build from the URL — never hand it to `fetchGeneric`.** That rule in the paragraph above only fires on a 404 or 410, because those are the only two answers `fetchGeneric` can read as "gone". Plenty of sites never send one, and it cannot tell *gone* from *blocked* on any of them: gitlab.com redirects a missing project to `/users/sign_in` and lands on a Cloudflare challenge (302 → 403, `<title>Just a moment…</title>`, no og tags); every Stack Exchange page answers a non-browser request with 403 whether the question is live or deleted; and Vimeo and Dailymotion both answer **200** for a video that is gone, with no og tags and a `<title>` that is empty or the bare site name. Each of those sends the link to Microlink, whose ~25 daily requests then go on rendering a page that says nothing — and the card ends up built from the URL regardless, just one quota unit poorer.

A dedicated fetcher is the only thing that can know better, and it knows for free, from a call it already made. What it must not do is throw that knowledge away: an API's *empty answer* is proof (SE's `{"items":[]}`, a 404 from GitLab's project API, from Vimeo's oEmbed, from Dailymotion's), while an API's *failure to answer* (a quota 400, a 5xx, a dead network) proves nothing and has to stay on the generic path. The two look identical in a `!result` check, which is exactly how the leak got in — `stackExchangeQuestionCard` returned `undefined` for both until 2026-09-04. Audited across every fetcher that day: SE, Vimeo, Dailymotion and GitLab were leaking, and were fixed; Wikipedia was already safe (its REST 404 comes with a 404 page); YouTube, GitHub, arXiv, LinkedIn, X, IMDb, Hacker News and Bluesky had their own URL-built fallbacks already. Twitch deliberately still falls through to Microlink — an SPA shell means the page was *not* read, not that it is gone, and that is the case Microlink exists for.

A parse that "succeeded" is checked for the SPA shell some sites serve a non-browser request: a `<title>` left as the raw URL slug where the real title should be. That test used to be the slug match alone, and it was wrong on its own — a title legitimately equals its slug whenever the thing is *named* by it. `pypi.org/project/requests/` declares `og:title` “requests”, its URL ends in `requests`, and so every PyPI package link was condemned as a placeholder, sent to Microlink, had the identical answer rejected a second time, and ended up a bare card — for a page that had described itself perfectly, `og:description` and `og:image` included. `looksLikePlaceholder` now requires the rest of the shell's signature as well, the half the comment always claimed and the code never checked: no description **and** no image. A page that supplied either told us something, whatever its title looks like. Fixed 2026-09-04; zhihu, the site the check was written for, could not be re-confirmed live (403 from here), but a 403 never reaches this test anyway — `fetchGeneric` bails on the status first.

**A 403 from a scripted probe is not evidence that the plugin is blocked.** `requestUrl` runs inside Electron and goes out through Chromium's network stack, so it presents a real browser's TLS and HTTP/2 fingerprint — which is what Cloudflare and friends actually profile, far more than the User-Agent. A `urllib`/`curl` probe from a terminal presents an obviously scripted one and gets the interstitial. On 2026-09-07 MyMiniFactory and Thangs were declared unreachable on exactly that evidence and then rendered perfect cards in Obsidian, Microlink untouched. The converse has now been measured too (Codeberg and SourceForge, 2026-09-16): a browser User-Agent can be refused *because* it is a browser UA without the rest of a browser's request, in Obsidian as from a script, while the plugin naming itself is let through - which is why `fetchGeneric` retries a 403 once with that UA. **And sometimes the challenge is `requestUrl` itself** (2026-09-18): Cloudflare answered Bandcamp with a 200 "Client Challenge" and Docker Hub with a 403 "Just a moment..." for every UA tried in Obsidian's console, while Node's `https` - from a script and inside Obsidian alike - got the real pages and the real 404s. So when the read is still a challenge after that retry (any 403, or a 200 whose whole title is an interstitial), `fetchGeneric` tries once more through `requestViaNode` on desktop before the fallback. So treat scripted probes as a **lower bound**: if the probe gets through, the plugin certainly will; if it is refused, the plugin may still succeed, and only a paste into Obsidian settles it. Anything in the rejected table justified by a bare 403 is suspect until re-checked that way. free3d and turbosquid were re-checked on that basis and **stayed rejected**: they render only through Microlink, never directly — so when re-checking, look at whether Microlink was called, not merely at whether a card appeared.

All endpoints re-checked at the network layer on 2026-09-01: each still returns the
fields the code reads. Rendering in Obsidian (image load, layout, downloaded-image
path) is a separate spot-check — see the list at the bottom.

## Generic path — verified

Go through `fetchGeneric` (og/twitter/JSON-LD tags), with the microlink fallback if the
user enabled it. Roberto is verifying these in Obsidian.

`appendSiteName` (markdown links only — a card shows `host` instead) appends the site name unless the title already ends in it after a separator. The recognised set is `-|·•:–—`, so a title like “Some story • Reuters” is left alone; `-` is what gets appended. Verified against the three news sites' real titles on 2026-09-03. One known false negative, contrived enough to leave: the separator split allows zero spaces, so a hyphenated title whose tail happens to equal the site name (“Anti-Trump rally” for a site called “Trump rally”) keeps its suffix off.

The last segment also counts as a match when it is a **whole-word prefix** of the site name, added 2026-09-04 alongside the MDN parser fix, which is what made the case appear: an MDN page is titled “… | MDN” while declaring `og:site_name` “MDN Web Docs”, and appending gave “… | MDN - MDN Web Docs”. Checked against every site's real titles before and after — the only labels that change are MDN's, plus one contrived false skip the prefix rule allows (a title ending “- The”, for a site called “The Verge”), which is not a shape real titles take.
